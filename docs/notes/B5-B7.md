## Decisions

| Decision | Alternatives | Evidence |
| --- | --- | --- |
| One shared `digest_payload` for the API and the snapshot exporter | Separate code paths | The saved copy must be exactly the live shape (API.md); one function makes that structural. Tests compare the exporter's output with `digest_payload` key for key |
| Expected digests in tests come from the ranker run on the fixture rows parsed straight from the file, not hand-written lists | Hard-coded expectations | Two independent paths (file → parser → ranker, and file → ingest → Postgres → `digest_payload` → HTTP) must agree item for item; named events are then checked on top: Elgi's results (85, its presentation on the card) in attention; Manappuram's Group CTO exit (senior, 70) and Asian Paints' Leo Puri appointment (55, two filings on one card) worth knowing. This matches DECISIONS.md's "1 attention, 8 worth knowing, 18 routine" |
| Tokens: HMAC-SHA256 over a small JSON claim set, stdlib only (`api/sessions.py`) | PyJWT, itsdangerous | No algorithm header, so no `alg` confusion; the MAC is checked in constant time before any parsing; exact claim set and types; canonical base64 only. One fewer dependency to audit |
| Claims: `sub` (investor), `ro` (read-only), `dep` (`core`/`full`), `iat`, `exp` (12 h), `v` | Server-side session table | Stateless fits a sleeping free instance; a token survives a restart (tested) |
| psycopg_pool, 1 to 4 connections, opened on first use, `check_connection` on every checkout, 5 s statement timeout, `reconnect_timeout` 60 s | One connection per request; no check | A fresh TLS connection to Supabase per request costs more than one check; the check replaces connections the pooler dropped while idle instead of failing a request. Recovery measured above |
| Pure ASGI middlewares, CORS written here (about 60 lines) | Starlette's `CORSMiddleware` | Starlette answers a refused preflight with plain text (`Disallowed CORS origin`), not the contract's error shape, and adds the CORS-safelisted headers to `Access-Control-Allow-Headers`; the brief asks for exactly Authorization and Content-Type |
| `/v1` refuses any request carrying an Origin that is not on the allow-lists (403) | CORS headers alone | Browsers send Origin on every cross-site request; a "simple" POST (no preflight) to `/v1/session/demo` from another website is refused before it does anything |
| Rate limits in memory, sliding 60-second window, a request counted in every window it falls in or none; IPv6 counted per /64 | Fixed per-minute counters; Redis or Postgres | One instance, one worker: Render's free plan cannot scale beyond one instance (https://render.com/docs/free). A sliding window has no burst at the minute boundary. Shared storage is needed only with more instances |
| Client address: `True-Client-IP` on Render, else the connecting address; never `X-Forwarded-For`; uvicorn started with `--no-proxy-headers` | Left-most X-Forwarded-For; uvicorn `--forwarded-allow-ips '*'` | See "Client address on Render" below |
| Sentry configured with `data_collection` (no user info, cookies off, bodies off, frame variables off, headers allow-listed to user-agent, content-type and origin), plus a `scrub` on events, transactions and breadcrumbs, plus a redacting log formatter | `send_default_pii=False` as briefed | In the pinned sentry-sdk 2.75, `send_default_pii` is deprecated and superseded by `data_collection` (https://docs.sentry.io/platforms/python/configuration/options/; also in the SDK source, which warns when it is set). `data_collection` with these values collects less than `send_default_pii=False` does (that still sends bodies and frame variables). A test captures what the SDK would really send for a failing request carrying a token, a cookie, a client IP and a database URL in the exception: none of them is in the event |
| Traces sampled at 5% | 100%; none | Latency data on demo traffic within Sentry's free quota |
| `/health` checks the database at most once per 10 s, waits at most 2 s for a connection, and never returns an error | A database call per request | It is unauthenticated, so the cache bounds database load from anyone pinging it; 2 s stays inside Render's 5-second health check (https://render.com/docs/health-checks), and a failing health check makes Render restart the instance |
| `render.yaml`: free plan, Singapore, `autoDeployTrigger: checksPass`, a build filter (api, pipeline/finn, db/seed, render.yaml) | Deploy on every commit | "After CI Checks Pass" deploys only when every GitHub check on the commit passes and never when none is found (https://render.com/docs/deploys). The filter avoids redeploying on web or docs commits |
| `PYTHON_VERSION=3.12.16` | Render's default (3.14.10 for services created after 3 Nov 2026); `.python-version` | The variable must be a full version and wins over `.python-version` (https://render.com/docs/python-version); 3.12.16 is the latest 3.12, released 25 Oct 2026 (https://www.python.org/downloads/), and CI tests on 3.12 |
| `version` in `/health`: the first 7 characters of `RENDER_GIT_COMMIT`, else `"unknown"` | A build-time file | Render sets `RENDER_GIT_COMMIT`, "the commit SHA for a service or deploy", at build and run time (https://render.com/docs/environment-variables) |
| No docs pages; `API_DOCS=1` serves only `/openapi.json` | Swagger UI behind the flag | Swagger's scripts would be blocked by the JSON-only CSP, so the page would load blank; the schema alone is still useful for the web app |
| `httpx2` in the dev requirements, not `httpx` | `httpx` | Starlette 1.10 warns that using `httpx` with its test client is deprecated and asks for `httpx2` (starlette/testclient.py) |
| All runtime dependencies pinned, direct and transitive | Direct only | Render, CI and a laptop install the same versions; checked with `pip index versions` on 15 Nov 2026 |
| The scratch-database setup moved from `pipeline/tests/conftest.py` into `tests/dbtools.scratch_database`, used by both suites | Copy it into `api/tests` | One definition of "Supabase-shaped"; the pipeline suite is unchanged in behaviour (166 pass) |

### Client address on Render

- Render's own article (1 Apr 2026): "All inbound traffic to Render web services passes through
  Cloudflare's global network before reaching your application", and it suggests reading
  `x-forwarded-for` (https://render.com/articles/how-render-handles-ddos-attacks).
- Render staff wrote in 2021 that the first entry of X-Forwarded-For is the real client
  (https://feedback.render.com/features/p/send-the-correct-xforwardedfor). A test on the same page
  (Mar 2024), a community thread (https://community.render.com/t/accessing-client-ips-in-a-node-express-app/36282),
  an article citing Render support (https://rohitpaulk.com/articles/render-rails-remote-ip) and a
  demo service run on Render (https://github.com/johnbeynon/header-test) all found that Render keeps a
  client-sent X-Forwarded-For and appends to it, so the left-most entry is whatever the client wrote.
  The same demo found `True-Client-IP` overwritten with the real address, and a spoofed
  `CF-Connecting-IP` refused by Cloudflare.
- So the limiter reads `True-Client-IP` when exactly one valid address is present, and otherwise
  the connecting address (Render's proxy), which makes every such client share one allowance:
  stricter, never spoofable. Off Render, it uses the connecting address. `CLIENT_IP_HEADER` can
  change the header without a code change.
- None of these headers is documented by Render itself, so this rests on the observations above.

## Where this differs from docs/API.md

None of the response shapes differ. These are status codes and cases the contract does not cover:

1. **405** (a known route, wrong method): HTTP 405 with code `not_found` and an `Allow` header. The
   contract's codes have none for it; `not_found` is the nearest ("unknown route").
2. **413** (body over 16 KB, by Content-Length or while reading a chunked body): HTTP 413 with code
   `bad_request`. The contract says such bodies are refused but lists `bad_request` under 400/422;
   413 is the correct HTTP status. A Content-Length that is not a number gives 400 `bad_request`.
3. **500** (an unexpected error): HTTP 500 with code `unavailable`, so the web app falls back to its
   saved copy, which is the right behaviour for any server-side failure. The contract has no 500 row.
4. **403 for a caller, not only a token**: `POST /v1/session/demo` with no Origin or an unlisted one,
   any `/v1` request with an unlisted Origin, and a refused CORS preflight all get 403 `forbidden`.
5. **`data_as_of` is `null`** until a filings ingest has succeeded (in `/health` and the digest).
6. **A session works only on the site that issued it**: a `core` token sent with the `full` site's
   Origin (or the reverse) gets 401. Requests with no Origin (non-browser clients) are accepted.
7. **503 from `POST /v1/session/demo`** if the demo investor row does not exist (seed not run).
8. **Sessions count towards the 60 a minute for `/v1`** as well as their own 10; refused requests
   count; CORS preflights do not.
9. **`hours` is read strictly**: digits only, so `1.0`, `+24`, ` 24` and `1e2` are refused with 422,
   which a lenient integer parse would have accepted. The message names the parameter.
10. **`HEAD /health`** is answered (some monitors use HEAD).

## Honest limits

- **Rate limits live in memory**: they reset when the instance restarts or redeploys (Render may
  restart a free service at any time, https://render.com/docs/free) and would not be shared by a
  second instance. Clients behind one NAT share one allowance.
- **Anyone can get a demo token**: that is decision 2 (one-tap, read-only). The Origin check is a
  browser control, not authentication: a non-browser client can send any Origin. Rate limits bound
  abuse; the demo token can only read the demo portfolio.
- **Tokens cannot be revoked one by one**: rotating `SESSION_SECRET` signs everyone out; expiry is
  12 h. The token is a bearer credential: if the web app keeps it in `localStorage`, an XSS on the web
  app could read it (B6's CSP and no `innerHTML` are the defence).
- **`data_as_of` can understate freshness**: ingest marks a filings run not ok if a results fetch in
  it failed, even though its filings were stored.
- **While the database is down**, each `/v1` request waits up to 5 s for a connection before 503,
  `/health` up to 2 s; `/health`'s `db` lags by up to 10 s (its cache).
- **Malformed HTTP** that uvicorn itself rejects (h11 400) is plain text, not the contract shape; such
  requests never reach the app.
- **Instance hours**: kept warm around the clock, one free service uses 720 h in November and 744 h in
  December, inside the workspace's 750 h (https://render.com/docs/free); no other free service may run
  in that workspace. Spun-down services use no hours.
- **GitHub disables scheduled workflows in a public repository after 60 days without activity**, and
  notifies only the user who last edited the cron line (GitHub's schedule notes, linked below).
- **Uvicorn exits with -15 after a clean SIGTERM shutdown** (it re-raises the signal after "Application
  shutdown complete"); the test checks for the clean shutdown, not exit code 0.

## Not verified

- Render's client-address headers: undocumented by Render; see above. If Render stopped setting
  `True-Client-IP`, the limiter would fall back to one shared allowance (safe, but strict).
- Whether Render's health checks count as traffic that keeps a free instance awake: the docs do not
  say. The keep-warm plan assumes they do not.
- Whether Render's Blueprint form accepts a blank value for a `sync: false` variable (relevant if the
  Vercel URLs are not known yet when the Blueprint is created).
- That Render offers exactly 3.12.16: Render says any released version from 3.7.3 onward is
  available. If the build reports the version missing, set `PYTHON_VERSION` to the newest 3.12 it has.
- The session pooler keeping `search_path` and `statement_timeout` for the life of a connection:
  `finn/db.py` relies on the same property (session mode), but nothing here could reach Supabase.
- UptimeRobot's exact screen labels, default request timeout and HTTP method.

## Keep-warm (B7)

Render's free service sleeps after 15 minutes with no inbound traffic and takes about a minute to
wake (https://render.com/docs/free). Two pings, so that one failing does not leave a gap:

1. **Primary: an external monitor every 5 minutes.** UptimeRobot's free plan has 50 monitors at a
   5-minute interval, HTTP and keyword monitors, and says it is "Good for personal and commercial
   projects" (https://uptimerobot.com/pricing/); its terms say it "is available for any use, including
   commercial and business use" (https://uptimerobot.com/terms/, changelog entry 26 May 2026). A 2025
   article reported a non-commercial restriction from Dec 2024, which UptimeRobot disputed in its
   comments (https://dev.to/r0tten0x/uptimerobot-free-plan-in-2026-the-limits-thatll-actually-bite-you-445g);
   FINN is a personal project either way. Alternative with no account limits: cron-job.org, free and
   donation-funded, up to once a minute, with failure notifications and a history of responses
   (https://cron-job.org/en/). Better Stack's free plan has 10 monitors, but its pricing page does not
   state the free check interval (https://betterstack.com/pricing).
2. **Backup: `keep-warm.yml`** every 10 minutes at :04, :14, ... (off the busy top of the hour), 100 s
   timeout for a sleeping service, one retry after 15 s, red if the API does not answer, a warning if
   the database is down; read-only token; manual run too. GitHub: "The `schedule` event can be delayed
   during periods of high loads"; "some queued jobs may be dropped"; shortest interval 5 minutes
   (https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule).
   Standard runners are free in public repositories
   (https://docs.github.com/en/billing/concepts/product-billing/github-actions).

## Karthik's steps (PowerShell, from the repository root)

1. **Install the two workflows and push.** `Move-Item -Force workflows-to-install\*.yml .github\workflows\`,
   then commit and push to `main`. Wait for both "CI" and "CI (API)" to go green: Render deploys only
   after every check passes.
2. **Create the Render service from the Blueprint.** Render dashboard > **New > Blueprint** > **Connect**
   next to `kdoesstuff/finn` > name it `finn`, branch `main`, Blueprint path left as `render.yaml` >
   review: one web service `finn-api`, Free, Singapore (https://render.com/docs/infrastructure-as-code).
   Paste the values it asks for (Render asks only at creation; later changes go in the service's
   **Environment** page):
   - `SUPABASE_DB_URL`: the same value as the GitHub secret of that name (Supabase > Connect > Session
     pooler, password filled in).
   - `SENTRY_DSN_API`: Sentry > project `finn-api` > Settings > Client Keys (DSN). Blank keeps Sentry off.
   - `ALLOWED_ORIGINS_CORE` and `ALLOWED_ORIGINS_FULL`: the production addresses of the two Vercel
     projects from B6, exactly, e.g. `https://finn-core.vercel.app` (comma-separate several). Until
     they are set, `/health` works but no site can start a session.
   - `SESSION_SECRET` is generated by Render: do not enter one.
   Click **Deploy Blueprint**.
3. **Find the URL and check it.** It is on the service's page in the dashboard
   (https://render.com/docs/your-first-deploy), of the form `https://finn-api....onrender.com`. Open
   that address with `/health` added: expect `{"ok":true,"db":true,"data_as_of":"...","version":"..."}`,
   the version being the first 7 characters of the deployed commit.
4. **Point the backup ping at it.** GitHub > Settings > Secrets and variables > Actions > Variables >
   New repository variable: name `API_URL`, value the service URL with no trailing slash (or
   `gh variable set API_URL --body "https://finn-api-53vw.onrender.com"` with the real URL). Then
   `gh workflow run keep-warm.yml` and check the run is green.
5. **Set up the primary monitor.** uptimerobot.com > sign up (free) > New monitor > type HTTP(s), or
   Keyword with `"db":true` to be alerted on a database outage too > URL: the service URL plus
   `/health` > interval 5 minutes > alert contact: your email > create. B7 is done after 12 hours with no gap over 10
   minutes in the monitor's log and no spin-down in Render's events.
6. **When B6 exists**, write the saved copy (it reads `SUPABASE_DB_URL` from `.env`):
   `python pipeline\scripts\export_snapshot.py --out web\public\snapshot.json` (D6 schedules this daily).
